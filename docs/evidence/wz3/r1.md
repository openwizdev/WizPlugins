# R1 ordering proof

Claim: a pending settle or snooze must refuse its eventual park write if the plugin has processed deletion or completed a wake for that same thread during validation. Earlier sequential deletion tests missed delayed host reads.

Proof: the SDK CLI/RPC boundary holds either `threads.get` or `threads.list`, processes deletion or each wake operation, confirms the empty store, then releases an old eligible response. Every stale park must fail without a recreated row or additional refresh publication. A multiple-reader case preserves deletion while older validations drain; a different-thread wake must not invalidate an unrelated park. Inputs and responses are synthetic; no live operations occur.

Before the fix, the focused SDK run reported 25 failures and one unrelated-thread control pass. After the fix, all 26 ordering cases pass. The red receipt is `red-r1.txt`.

Implementation: parking captures a per-thread revision before its first awaited host read. Successful wake deletes increment that revision before refresh; deletion also marks the pending state deleted before cleanup. The final park check rejects changed revisions without writing or publishing. A pending-read count keeps deletion knowledge until all older validations drain, after which the transient state is removed. Fresh requests still require authoritative host reads; no lifecycle fields are written to host threads.
